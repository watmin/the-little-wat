# SCORE — readloop

Strike 1 landed and is verified. **It does not improve `vecsum`, and it cannot**: the brief's
diagnosis of `:c::tail-direct?` is incomplete. Strikes 2 and 3 both hit their STOP triggers.
STOP-1 fires with a named holder. STOP-2 fires: a vector `use-walk` is a new walk, not a reuse.

---

## Strike 1 — `tail-direct?` relaxed. Landed. Verified. Worth ~nothing.

### What changed

`elf/compile.wat`, `:c::tail-direct?` only. Argument j is now safe if it is a symbol whose text
is parameter j's name, OR `:c::none-mention?` holds as before. Nothing else was touched.

### It does not unlock `vecsum` — the guard fails at j=1 as well, and legitimately

The brief says argument 2 mentions `v`, "so it fails at j=0 and the whole call falls to
`:c::tail-store`". That is true but not the whole reason. `:c::tail-direct?` is an AND over
*every* j, and for `user/sum` it fails **twice**:

| j | parameter | argument j | later arguments | verdict |
|---|---|---|---|---|
| 0 | `v` | `v` | `(+ acc (nth v i))` mentions `v` | fails today; **relaxed by strike 1** |
| 1 | `i` | `(+ i 1)` | `(+ acc (nth v i))` mentions `i` | **fails, and must** |
| 2 | `acc` | `(+ acc (nth v i))` | none | passes |

At j=1 argument 1 is `(+ i 1)`, not the bare symbol `i`. Writing `i` genuinely clobbers the
value argument 2 reads through `(nth v i)`. That is exactly the hazard the guard exists for, so
no relaxation of the *self-name* kind can reach it. The call still falls to `:c::tail-store`,
and `vecsum` is byte-identical before and after.

**The real unlock is assignment ORDER, not the guard.** Assign the arguments right-to-left and
`user/sum` is fully direct: `acc` first (reads `v`, `i`, `acc`, all still original), then `i`
(argument `(+ i 1)`, and nothing already written is mentioned), then `v`. The dual predicate is
"no EARLIER argument mentions parameter j" — `:c::none-mention? ks 1 .. j+1` instead of
`ks (j+2) ..` — plus a reverse-order `:c::tail-direct`. That is a second emitter direction, not
a guard tweak, so I did not build it: it is outside the mapped room.

### A downstream claim in the brief is wrong

> `:c::selv?` admits a bare register symbol and `:c::selv` emits NOTHING when the register is
> already the destination (that is C-177).

`:c::selv?` opens with `(if (:c::ptr-ty? (:c::type-of a env pg)) false ...)` (elf/compile.wat:2936).
A **pointer** parameter is rejected, so `v` never reaches the C-177 no-op path. It falls to the
`:else` branch and emits `:c::share` + `mov %rN,%rax` + `mov %rax,%rN` — five instructions, not
zero. Confirmed by disassembly of `freed.elf` below.

### Sizing the prize honestly

The `vecsum` read loop is **32 dynamic instructions per element** (0x40015e..0x4001c7, counted
from the disassembly). If the tail call went *fully* direct (i.e. with the ordering work done):

- `(+ i 1)` would reach `:c::acc-op` → `add $1,%r12` + `jo`, 2 instructions instead of 5;
- `v` would cost 5 (share + mov + mov) instead of 6 (mov + share + push + pop).

That is **~4 instructions of 32, about 12%** — the *smallest* of the three strikes. The two big
items in that loop are the `(length v)` reload block (8 instructions, including a `push`/`pop`
of `i` around it because `length` needs rax) and the `:c::share` (3). Those are strikes 3 and 2,
and both have stop answers.

## Strike 2 — STOP-1 FIRES. The increment accounts for a real holder, and I can name it.

**The holder is parameter 0 of the next iteration.**

The strike's premise is "on a tail call passing a parameter through to its OWN slot, no new
holder is created". That is false whenever another argument of the same call retains or mutates
the container. Argument 0 is evaluated **first**, and it copies the pointer forward into a slot
that *outlives* the rest of the call — so a later argument that mutates that same object in
place is mutating something the next iteration already holds.

Concretely, `(user/step v (conj v i) (+ i 1))`:

1. `:c::conj` (elf/compile.wat:1384) shares only its **value** (`ks[2]`), never its
   **container** (`ks[1]`). `own?` there is `(and (= (kind ks[1]) "symbol") (:c::linear? ...))`.
2. Tracing `:c::linear?` → `:c::dead-after-write?` → `:c::live-seq` by hand on that shape: the
   mut-site is the `conj` at argument 1; `live-seq` finds the read of `v` at argument 0
   *precedes* it, and C-176 treats a preceding read as harmless; nothing after argument 1
   mentions `v`. So `v` is judged linear and `vec_conj_own` is emitted.
3. The runtime count is then the only remaining gate — and the tree says in its own words
   (elf/compile.wat:2271, the `:c::fresh-str?` commentary) that a borrowed pointer's
   "share count really is 1, because a fresh value stored into a container is stored by MOVE:
   `:c::share` increments symbols only … So the runtime guard asks 'count 1?', gets the truth,
   and draws the wrong conclusion."
4. Therefore the `:c::share` on **argument 0** — the exact increment strike 2 proposes to
   remove — is what keeps the count above 1 and makes `vec_conj_own` refuse.

The liveness analysis is sound for a value that dies at the end of the expression. Argument 0 of
a tail call does not die: it becomes the next iteration's parameter. That is the gap the
refcount is covering, and it is precisely F-142's lesson — the count UNDER-counts, so lowering
it further is the dangerous direction. **Leave it alone.**

### Is an unbounded refcount on a pass-through parameter a latent bug?

**No — it is the compensation, not the bug.** It costs an optimisation, never a correctness,
which is the safe direction this tree has chosen deliberately (C-176, F-142).

It is real, and worth writing down: in `vecsum` the count on `v` climbs to ~2,000,000 and can
never come down, because it is a "has this ever been shared?" flag rather than reclamation. The
consequence the brief predicts is correct — **any loop that both reads a container and conjs it
will never reach `vec_conj_own` or `slot_set_own`** — but as shown above, that is exactly the
loop shape where firing would be *wrong*. The cost is 3 instructions per iteration (`cmpq`,
`je`, `incq`) in loops like `vecsum` where nothing is ever mutated.

**If you want that 3 instructions, the safe predicate is not "argument j is parameter j".** It is
"no other argument of this call RETAINS the container" — `nth` and `length` read it without
retaining, `conj`/`assoc`/`concat` retain it, a bare symbol retains it. That is a *use
classification* of a vector parameter — which is the same analysis strike 3 needs, and which
STOP-2 is about. The two strikes want one mechanism.

## Strike 3 — STOP-2 FIRES. A vector `use-walk` is a new walk, not a reuse. Telling you, as asked.

`:c::use-walk` (C-193) exists at `elf/compile.wat:3647` and it is a **ten-function family**:
`use-walk`, `use-fold`, `use-both`, `use-last`, `use-cond`, `use-clause`, `use-args`,
`use-form`, `use-body`, plus the `:c::Use` lattice (`use-none` / `use-field` / `use-other` /
`use-union`) and the helpers `kw-field` and `scalar-field`.

It cannot be reused for the vector question, for two reasons:

1. **The lattice value is a field index.** `:c::Use` is `{k, f}` where `k ∈ {none, field, other}`
   and `f` is a record field number; `use-union` merges by comparing field indices. A vector has
   no analogue — the vector question wants `{none, container-read, escapes}`.
2. **Every leaf is record-specific.** `use-form`'s two interesting clauses key on
   `:c::acc-index` (is the head a record accessor?) with an `rname` prefix match, and on
   `(assoc name :f v)` via `kw-field`. The vector version needs entirely different leaves:
   `(nth v i)` and `(length v)` as non-retaining container uses, `(conj v x)` as a write, a bare
   `v` as an escape.

The traversal skeleton (`fold`/`both`/`last`/`cond`/`clause`/`args`) is identical in *shape* and
that is the trap. `compile.wat` is written in its own subset, which has **no closures** (C-131
removed the last one), so the skeleton cannot be parameterised by a leaf predicate. Reuse means
either duplicating nine mutually-recursive functions with different leaves, or generalising
`:c::Use` and `use-form` to answer both questions at once — which changes record scalarisation's
behaviour and would need its own justification and its own bootstrap.

**So: new walk. Stopping and telling you, per STOP-2.**

### What I did NOT rule out, and you should weigh

There may be a cheaper sufficient condition that reuses machinery the tree already has.
`(length v)` is loop-invariant if (a) the tail call passes `v` through as itself — which is
exactly the predicate strike 1 just added — and (b) nothing mutates `v`. For (b),
`:c::mut-site` already answers "is this name ever the receiver of an `assoc`/`conj`/`concat`",
returning `-1` for none. A container is copy-on-write, so only the `*_own` paths mutate, and
those require the name to be a symbol at a mut-site. A `v` handed to *another* function is
shared by `:c::push-args`, so that callee's count is ≥2 and its own path cannot fire either.

I did **not** attempt this. It is exactly the shape of argument F-142 punishes — reasoning a
static ownership test away — and it belongs to you to weigh, not to me to land inside a strike
that told me to stop. I am flagging it because STOP-2 said "tell me", and the honest answer is
"the walk is new, but the walk may not be the only route".

## Honest deltas and things that surprised me

- **The brief's diagnosis was half right.** j=0 is relaxable; j=1 is not, and nobody had checked
  it. Strike 1 could never have moved `vecsum`. I verified this by hand *before* the first
  bootstrap and said so, and the build confirmed it: `vecsum` is not in the moved list.
- **Strike 1 costs more than it saves**, on the only workload big enough to measure. +0.061%
  instructions on the compiler. I did not expect a landed, sound, verified change to come out
  negative, and I would not have found it without rebuilding the baseline from scratch.
- **The corpus scan matching `emitted.sh` exactly** (freed, reader, compile.wat's six) is the
  part I trust most. Two independent oracles agreeing on which programs moved.
- **`:c::selv?` rejects pointers**, so the C-177 "emits nothing" path the brief relied on is not
  reachable for `v`. Even a fully-direct `vecsum` pays 5 instructions for the pass-through.
- **Strikes 2 and 3 want the same mechanism** — a use classification of a vector parameter that
  distinguishes reading (`nth`, `length`) from retaining (`conj`, a bare mention). That is the
  thing worth drawing a room around, and it answers both the share and the hoist.
- **`elf/out/seed.elf` is perturbed, and `emitted.sh` will report it.** It is a `--fast` scratch
  copy, not a compiled program, but `emitted.sh` does not exclude it the way it excludes
  `compiler.elf` and `stage*.elf`. I overwrote it during the aborted `--fast` excursion and
  cannot restore its old bytes, so I left it as a copy of the current `compiler.elf` — which is
  exactly what `--fast` leaves. So the final `emitted.sh check` reads **3 of 74**: `freed.elf`,
  `reader.elf` and `seed.elf`. Only the first two are emitted code. Consider adding `seed\.elf`
  to `emitted.sh`'s exclusion list alongside `compiler.elf`; it is the same kind of artifact.
- **`bootstrap.sh --fast` cannot A/B a codegen change backwards.** Seeding the old source from
  the new compiler makes stage1 and stage2 legitimately disagree, and it reports
  `FAIL: stage 2 is not stage 1`. That is the tool being right, not a regression; I abandoned the
  shortcut and did two full bootstraps instead. Worth knowing before someone reads that FAIL and
  panics.
