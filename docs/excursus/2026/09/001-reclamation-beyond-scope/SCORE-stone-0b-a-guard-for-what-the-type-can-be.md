## Row 4 — the derivation · **written, in `:c::count-hex`'s prose and here**

What decides a guard. **`cmp [rax-8],0 ; je`** protects a count-0 **write**, because the `cmp`
already dereferences `[rax-8]`. So it is needed only by a type whose value can have count 0.
**`cmp rax,0x1000 ; jb`** protects a small-integer tag.

**Count 0 means literal, and only a literal.** Every allocator writes a count of at least 1:

| allocator | writes | `elf/lib/runtime.wat` |
|---|---|---|
| `vec_new` (records, henum payloads) | `[p-8] = 1` | `:548` |
| `varr_new` (every Vector form) | `[p-16] = flat`, `[p-8] = 1` | `:672-673` |
| `vec_conj_own` copy path | `[p-8] = arm-own` | `:614-615` |
| `tree_push`, `tree_from_arr` | `[p-8] = heap-arm` | `:845`, `:874` |
| `vec_conj` | `[p-8] = heap-arm` | `:939` |
| `slot_set` (`assoc`) | `[p-8] = 1` | `:969` |
| strings: `str_cat_own`, `str_subs`, `i64_to_str`, `read-hex`, `read-file` | `heap-arm` | `:162`, `:1001`, `:1113`, `:1377`, `:1482` |

A count of 0 is written in exactly one place: `:c::static-str`, `elf/compile.wat:1438-1451`
(`(:asm::le 0 8) (:asm::le n 8)`, at `:1450`, with the comment *"a count no allocation can
produce"* at `:1446`). Its callers are `:c::str-lit` (`:1457`) and the `assert` message
(`:3359`), and both are Strings. The data tail's only other writer is `:c::print-string`
(`:4023-4028`), which writes raw bytes that no value ever points at. The compiler emits no
inline allocation; a grep for `r15` writes in `compile.wat` finds only the entry stub's
`lea r15` (`:5681`).

**The table:**

| type | what a value can be | evidence | guard emitted |
|---|---|---|---|
| `str` | a data-tail literal, count 0, read-only | `compile.wat:1438-1451`, `:1457` | **literal** (unchanged) |
|  | or a heap string | `runtime.wat:162`, `:1001`, `:1113` | |
| `vec:` | only a heap block, count ≥ 1 | `:c::vec-form` calls `varr_new` for every form, zero elements included (`compile.wat:3365-3372`); `conj` → `vec_conj`/`vec_conj_own` (`:1886`); runtime rows above | **none**: `incq [rax-8]` |
| `rec:` | only a heap block, count 1 | `:c::rec-form` → `vec_new` (`compile.wat:3622-3630`); `assoc` → `slot_set`/`slot_set_own` (`:3334`) | **none** |
| `henum:` | a heap block (`vec_new(1+n)`), or a unit variant's tag | `:c::variant-form` → `at-vnew` (`compile.wat:3617`); ladder `:907`; *"A unit variant is its TAG, in every tier"* `:1974`; threshold 4096 `:921` | **tag** only |
| `penum:` | its payload's value itself (tier 1 allocates nothing), or a unit tag | `:c::variant-form` tier-1 arm is the field expression alone (`compile.wat:3603-3606`); ladder `:906`, `:914` | **tag, plus whatever the payload needs**: `penum:S;str` → tag+literal; `penum:O` over a Vector → tag only |

`penum:` recurses through `:c::maybe-literal?` on the payload type (`compile.wat:3114-3125`), so
a `penum` over a `penum` over `str` keeps the literal guard. **STOP-2 did not fire.** No
non-string pointer type can be a read-only literal or live outside the heap. Records reached
through registers (`:AtReg`, `:Reg`) point into heap records; there is no stack-allocated record
or Vector, and no argv Vector. The one "outside the heap" value, the unit tag, is exactly what the
tag guard is for.

## What surprised me

1. **Instructions and cycles came apart, as EXPECTATIONS predicted.** −5.34% instructions
   against 0a bought −1.1% to −1.4% cycles. The corpus compile is now +2.4% in instructions and
   about +5.2% in cycles over `dada88f`. If the builder's bar is time, the next stone is the
   header-word write, not the guard.
2. **`penum:` is a trap in the probe too, not only in the table.** The `penumtier` mutation, which
   is the obvious "tier 1 is never a literal" shortcut, segfaults on the first literal payload.
3. **No probe covered a read out of a trie.** Every F-188 fixture has at most 4 rows.
   `count-trie.wat` is the first, and making it able to fail took two attempts: the row has to
   carry `arm-own`, have room in its block, and not be the youngest allocation.
4. **F-189's +10.64% cannot be re-measured**: the workload is the compiler source, and it has
   changed twice since. On today's input the stone-0/0a gap is +8.15%.

## Method notes

Every `wat` run and native run took `timeout -s KILL`. The tree was untouched during bootstrap,
`elf-run` and `vs-c`. The baselines, mutations and measurements all ran in scratch copies. Every
text replacement in every edit script asserted exactly one match. Two probe drafts failed on my
own errors: a `sed` that dropped a `]`, which made the compile hang until the timeout killed it,
and `core/length` on a String. Both were fixed with asserted edits before any number was taken.
`count-hex`'s and `maybe-literal?`'s `cond`s end in `(:else …)`, and there is no `_`. Every
number above was measured in this session.

**The tree is dirty and nothing is committed.**

### A correction against the EXPECTATIONS — the orchestrator's error, not the strike's

EXPECTATIONS asked for cycles beside instructions "whatever they say", and framed the outcome as:
*if instructions recover and cycles do not, the remaining cost is the memory touch.* **The repo's
own measurement rule forbids that inference.** F-154 (`FINDINGS.md:12849`): code layout alone moved
one program's cycles by fifty percent, and the rule is **"do not attribute a sub-25% difference to
a codegen change measured on one program in one build."** The cycle deltas here are 1–6%, on one
program, across three builds. Two consistent rounds rule out run-to-run noise; they cannot rule out
layout, which is fixed per build and therefore reproducible without being attributable.

So the strike's *"cycles recovered only 17.6% / 23.0% … what remains is probably the memory
touch"* is not supported — and not refuted. It was inferred by elimination, from a comparison the
brief should never have asked it to make. Instructions, pinned, are the metric this repo trusts at
this size, and on instructions the stone met its bar.

**The remaining +2.382% is recorded, not drawn.** No stone is drawn to chase it until it is measured
at a level that can see it: uops and retiring%, or a same-binary control that varies only the
`incq`. That is F-154's rule applied forward.
